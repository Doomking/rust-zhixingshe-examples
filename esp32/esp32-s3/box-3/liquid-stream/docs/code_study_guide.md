# Liquid Stream: 嵌入式高性能流体模拟代码研读指南

本指南将带你深入了解项目的代码架构，从程序的入口点开始，逐步剖析硬件初始化、物理模拟和极限图形渲染的实现原理。

---

## 1. 整体架构概览

项目采用**分层架构**，将复杂的物理模拟与底层的硬件操作完全解耦：

- **`main.rs`**：系统编排器，负责初始化硬件、启动传感器线程，并运行核心仿真主循环。
- **`hal.rs`**：硬件抽象层（HAL），封装了 ESP32-S3 的 SPI、I2C 和显示屏初始化逻辑，提供了极限性能所需的裸机控制。
- **`physics.rs`**：物理内核，基于粒子（Particle）和网格（Grid）的混合算法，实现了流体的重力感应、不可压缩性和碰撞逻辑。
- **`render.rs`**：渲染引擎，将物理粒子的状态转化为帧缓冲区的像素，并利用 DMA 技术实现高速刷屏。

---

## 2. `main.rs`: 程序的灵魂

主函数是整个系统的控制器。其逻辑非常清晰：

1.  **硬件启动**：调用 `hal::init_hardware` 获取屏幕和 I2C 的控制权。
2.  **传感器解耦**：启动 IMU（陀螺仪）独立线程，通过异步方式获取设备的倾斜角度（重力向量）。
3.  **核心循环 (Game Loop)**：
    - **获取重力**：从传感器读取当前的重力向量，并映射到屏幕坐标系（注意：需要反转 Y 轴以符合屏幕坐标惯例）。
    - **物理步进**：`fluid.step(dt, gravity)`。让物理引擎计算这一帧内粒子的位置变化。
    - **同步渲染**：`render_engine.render_fluid(...)`。将计算好的粒子位置绘制到缓冲区，并推送到物理屏幕。
    - **性能监控**：每秒打印一次物理耗时、渲染耗时和当前的 FPS。

---

## 3. `hal.rs`: 极限性能的基石

在优化过程中，我们对这个文件进行了“手术级”重构，目的是绕过高级驱动的性能瓶颈。

- **`init_hardware` 的特殊逻辑**：
  - 我们首先利用 `mipidsi` 库对屏幕进行标准的 ILI9342C 序列初始化。
  - **关键点**：初始化完成后，我们立即调用 `.release()` 释放了显示驱动。这样做是为了拿回底层的 **SPI 设备句柄** 和 **DC（数据/命令）引脚**。
- **DMA 配置**：
  - 通过 `spi::Dma::Auto(32768)` 开启了 32KB 的大容量 DMA 通道。这使得我们能以块的形式，直接将内存中的图像数据搬运到 SPI 控制器，而不需要 CPU 逐个像素地去操作。

---

## 4. `physics.rs`: 流体的数学奥秘

这里的流体模拟不是简单的“移动粒子”，它采用了 **PIC/FLIP 混合算法**：

1.  **网格与粒子的协同**：
    - 粒子负责存储精确的位置和速度。
    - 网格（MAC Grid）负责处理“不可压缩性”。流体不会重叠，也不会消失，这是通过求解泊松方程（Gauss-Seidel 迭代）实现的。
2.  **PBF 粒子分离**：
    - 为了防止粒子因为重力被压成“一张纸”，`push_particles_apart` 逻辑强制粒子之间保持最小 6 像素的距离。
    - **空间哈希 (Spatial Hashing)**：为了让碰撞检测不变成 O(N²) 的复杂度，我们把屏幕分成了许多小桶，粒子只和相邻桶里的邻居进行碰撞检测。
3.  **隐形障碍物**：
    - `init_walls` 中定义了宏观的 `SOLID` 格子。物理引擎在更新粒子速度时，会自动查表，确保粒子遇到这些区域会发生反弹。

---

## 5. `render.rs`: 像艺术家一样绘图

由于物理引擎计算的是浮点坐标，渲染引擎的任务是把这些“数学点”变成“视觉像素”。

1.  **Blob 渲染（光点融合）**：
    - 每个粒子都被绘制为一个半径为 4 的实心圆盘。由于圆盘之间会相互重叠，视觉上会形成连续、有张力的流体表面。
2.  **全息框绘制**：
    - 代码中硬编码了一个“全息力场” UI。它会检测当前坐标是否处于边界、角落或内部，并绘制对应的青色高亮或深蓝色底色。
3.  **裸机刷屏 (Direct Blitting)**：
    - 这是性能飞跃的关键。我们不再调用 `draw_pixel`。
    - **RAMWR 命令**：我们直接通过 SPI 发送 `0x2C` 指令，告诉屏幕：“接下来我要发送一整块内存数据，请直接填满显存。”
    - **大端序预处理**：颜色常量都使用了 `.to_be()`。这样当我们将 `u16` 缓冲区强转为字节流发送时，颜色顺序在 SPI 线上是完全正确的，无需 CPU 再次转换。

---

## 6. 学习建议

- **想研究物理**：重点看 `FluidSim::step` 方法中的迭代顺序（粒子到网格 -> 求解 -> 网格回写粒子 -> 粒子排斥）。
- **想研究驱动**：研究 `hal.rs` 中如何获取 `SpiDeviceDriver` 以及 `render.rs` 最后那段 `unsafe` 的字节流强转。
- **想研究 UI**：看 `render_fluid` 中如何通过逻辑判断绘制全息框的各个组件。

这是一个典型的“计算密集型 + IO 密集型”嵌入式项目，通过它你可以学到 Rust 如何在保证安全的前提下，通过底层操作压榨硬件的每一分算力。
