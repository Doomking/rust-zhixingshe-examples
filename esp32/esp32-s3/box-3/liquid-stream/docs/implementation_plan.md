好，进行第三阶段。要求也要达到工业级的架构水准。# LiquidStream 实施计划与技术方案

基于 PRD 需求，特制定以下实施计划与技术落地细节，以确保在 ESP32-S3 BOX 3 上顺利实现基于 Rust 的高性能流体交互系统。

---

## 1. 里程碑与阶段计划规划

### 阶段一：项目初始化与基础设施搭建 (Day 1-2)
* **目标**：建立可编译、可烧录的 ESP-IDF Rust 标准库 (STD) 工程，并完成核心外设的打通。
* **任务清单**：
    1. 使用 `cargo generate esp-rs/esp-idf-template` 初始化标准库项目。
    2. 配置 `.cargo/config.toml` 以支持 `cargo run` 一键构建、烧录与监控。
    3. 配置 `sdkconfig.defaults`，开启 PSRAM、FPU 支持与 LTO 优化。
    4. 集成 `esp-idf-hal`与`esp-idf-svc`，打通 LCD 屏幕 (如通过 SPI/DMA) 与 I2C 外设。
    5. 实现双缓冲机制，验证全屏刷新帧率能否满足基础要求。

### 阶段二：传感器与输入系统 (Day 3-4)
* **目标**：引入 BMI270 数据读取平台，将设备姿态实时转化为物理引擎中的力场。
* **任务清单**：
    1. 在 `imu.rs` 编写 I2C 通信及 BMI270 的初始化序列。
    2. 在独立线程（或通过外设中断/定时器）以 >50Hz 的频率采集三轴加速度与陀螺仪。
    3. 使用低通滤波（Low-Pass Filter）平滑输入，将姿态映射为 2D 二维重力向量 `gravity: Vec2`，通过并发安全的机制喂给主循环。

### 阶段三：流体引擎原型开发 (Day 5-7)
* **目标**：实现 `fluid.rs` 基础逻辑，完成粒子动力学的基本验证。
* **任务清单**：
    1. 设计并实现 `Particle` 结构体，以及 `FluidSim` 全局容器。
    2. 基于欧拉积分实现速度与位置的更新计算。
    3. 实现与 320x240 屏幕边界的非弹性碰撞反弹机制。
    4. 将粒子位置可视化到屏幕上，确保核心循环能跑通并达到 30 FPS，针对 `glam` 的性能进行初步压测。

### 阶段四：深入 FLIP/流体算法优化 (Day 8-11)
* **目标**：引入网格，实现流体由于压力差导致的不可压缩性，这也是最有挑战的环节。
* **任务清单**：
    1. 构建等距网格 (Grid Size 例如 40x30)，实现粒子特征向网格转移的 P2G (Particle-To-Grid) 算法。
    2. 开发 Jacobi 压力求解器进行数次迭代，剔除速度场中的散度。
    3. 将修正后的网格速度重新插值回粒子上的 G2P (Grid-To-Particle) 传导。
    4. 调试与 Profiling：如果计算量耗尽 MCU 算力，调整宏观物理网格的精度或者压力迭代的次数以换取帧率。

### 阶段五：渲染与交互打磨阶段 (Day 12-13)
* **目标**：从“像素点”变为具有水质感的炫酷视觉表现，并加入业务逻辑上的障碍碰撞。
* **任务清单**：
    1. 静态碰撞支持：为 UI 图标或 "Infinite Light River" Logo 区域预设二进制掩码，流体粒子不能穿越。
    2. 视觉表现增强：基于密度映射调色，越密集的粒子呈现高亮的“电子水”材质。
    3. 测试各种极端翻转姿态，防止算法跑飞。

### 阶段六：质量保证与发布 (Day 14)
* **目标**：交付高质量和持续稳定的固件与源码结构。
* **任务清单**：
    1. 开发自动降级策略（即监控 `step()` 时长，超限自动剔除部分水粒子或者降低物理迭代）。
    2. 内存健康检查（排查动态分配引发碎片的风险）。
    3. 编写代码的 README 说明档，提供打包编译与执行指导。

## 2. 核心技术架构设计细节

### 2.1 依赖结构与版本选型
在 `Cargo.toml` 中配置关键依赖和硬件优化项：
```toml
[dependencies]
esp-idf-hal = "0.42"      # HAL层操作外设
esp-idf-svc = "0.48"      # Wi-Fi及运行时服务 (按需)
glam = { version = "0.24", features = ["libm"] } # S3 FPU 加速的向量数学运算
embedded-graphics = "0.8" # UI层和图形层
# 依据实际使用的屏幕，补充对应的 display 驱动（如 mipidsi 等）

[profile.release]
opt-level = 3          # 开启最大程度的编译器优化
lto = "fat"            # 跨 Crate 链接优化
codegen-units = 1      # 提升最终执行效率
panic = "abort"        # 大幅降低二进制资源开销
```

### 2.2 多核并发模型 (Core 0 vs Core 1)
ESP32-S3 是双核 MCU，我们需要充分发挥其双线程优势：
* **Core 0 (Data/Network/Sensors)**: 分配给 Wi-Fi（若需要）、BMI270 IMU 轮询采集线程。使用 `std::sync::Arc<RwLock<Vec2>>` 持有当前的物理倾角映射数据。
* **Core 1 (Physical Engine & Render)**: 专注于大负载运算。使用一个主 `loop {}` 进行 `FluidSim::step()` 并调用 DMA 发送 Framebuffer。由于双缓冲的使用，我们可以做到渲染（DMA发送上一帧）物理步进（求解最新帧）同时执行。

### 2.3 关键内存存放 (Internal SRAM vs PSRAM)
* **Particle 结构体数组**：对于 1000 乃至更多粒子的状态记录，推荐分配在外部的 **PSRAM** 中。我们可以通过构建专门落在 PSRAM 的 `Allocator` 避免占用宝贵的内部空间。
* **网格(Grid)高频计算资源**：由于 FLIP 中网格（例如 40x30 = 1200 个单元）被极为频繁地读写（散度、压力迭代），应确保其保留在内部 **SRAM** 中以利用内部总线上更低延迟的 Cache。

### 2.4 可用替代/备选解法 (Fallback Plan)
1. **渲染瓶颈备选方案**：如果每帧清空画布重绘太慢，可以将流体的渲染区局限在特定的物理沙盒范围内，不进行全屏 Framebuffer 更新。
2. **算法过度消耗备选方案**：若 30 FPS 下 ESP32-S3 SPH / FLIP 求解性能均达不到理想，转为使用 PBD (Position Based Dynamics) 实现，PBD 可以较好处理流体视觉，通常收敛速度较块，可节省算力以支撑更极端的 FPS。

## 3. 架构设计核心原则

为保证代码基在后续迭代中具备工业级的可靠性，本项目的架构设计强制遵循以下三大约束：

### 3.1 模块化 (Modularity)
通过严格的**关注点分离 (Separation of Concerns)**，将系统解耦为多个独立子模块，避免代码耦合引发的牵一发而动全身：
- **`hal` (硬件抽象层)**：将 ESP32 特有代码（SPI, I2C, DMA）隔离。业务代码绝不能直接操作寄存器，只能通过 `Box/Trait` 依赖注入。
- **`physics` (物理内核)**：纯逻辑实现，不依赖任何特定芯片（纯 `no_std` 或跨平台 `std`），其输入是重力向量与时间增量 `dt`，输出是粒子坐标群数组。
- **`render` (渲染层)**：专门对接 `embedded-graphics` 或 framebuffer，将 `physics` 输出的坐标点渲染为具有水质感的像素矩阵。
- **这种好处在于：** 当后续更换屏幕或移植到其他芯片体系库时，物理与核心计算逻辑一行都不用改。

### 3.2 可扩展性 (Scalability)
基于 Rust 的 Trait 机制与消息传递设计，确保功能伸缩自如：
- **插拔式输入源**：目前使用 BMI270 提供重力流，未来如果加入麦克风（声波震动流体）或者触摸屏（指尖排斥流体），只需增加实现了 `InputSource` trait 的结构体，引擎主体框架无需变更。
- **灵活的碰撞系统**：引入通用的 `Collider` trait，任何带有 `check_collision(&mut Particle)` 行为的障碍物（圆形、矩形、“无限光河”位图Logo）都可以被动态压入运行时列表。
- **算力自适应伸缩**：支持根据芯片压力动态伸缩网格分辨率和粒子数量，以保证核心帧率的稳定。

### 3.3 可维护性 (Maintainability)
针对长期技术生命周期的防腐蚀设计：
- **脱机化单元测试**：由于 `physics` 模块不含芯片强依赖，所有的物理逻辑及数值溢出问题均可通过 `$ cargo test` 直接在 PC 上进行高覆盖率测试。
- **强类型配置约束**：不散落任何 Magic Number。将物理参数（粘度、重力常数、阻尼系数）和屏幕参数（分辨率、SPI 频率）抽象为显式的 `Config` 结构体，集中在项目入口解析配置。
- **完善的日志追踪**：在关键链路（中断触发频率、DMA 传输带宽、物理引擎每帧耗时）植入分级日志 `log::info!`, `log::trace!`，通过 `esp-println` 输出，便于在不打断系统流程的情况排查卡顿原因。
