## 2. Cyber-Hub 能做什么？有什么用？

*[图片占位符：插入 Cyber-Hub 放在电脑桌面上的实测照片、或 UI 运行状态的多图拼合]*

所以，基于这款带屏硬件，我们到底折腾出了一套什么好玩的东西？

我们给它取名叫 **Cyber-Hub**。它并不是一块放在桌边单纯用来“看看时间”的电子表，而是你电脑系统数据、真实世界环境数据的汇接中枢。它为你提供以下三大核心作用：

1. **桌面主机的“副屏监控仪”**：通过与电脑主机后台连接，它能如同赛博黑客一般，以极简粗犷的块状字体在你的桌面上无延迟刷新你的 CPU 与内存（RAM）占用率，让你在打游戏或跑程序时时刻掌控机器状态。
2. **极客风时钟与气象站**：无需繁琐的多级菜单配置，连上 WiFi 即刻获取准确公历并完成毫秒级时区同步，还能从网络拉取本市现在的实时天气状况和风速。
3. **近场环境感知器**：通过读取内置传感器，精准感受你所在房间此时此刻真实的温度与湿度。

接下来，我们就来看看这些花里胡哨的功能，在底层是如何通过 Rust 的代码逻辑优雅实现的。

## 3. 整体架构：多线程 IO 与状态共享

在传统的 C 语言单片机裸机开发中，通常是一个超级大的 `while(1)` 循环加上各种错综复杂的状态机，牵一发而动全身。但在 Rust 中，基于 ESP-IDF 提供的通用标准（`std`），我们可以非常优雅地采用**解耦的多线程架构**。

在 Cyber-Hub 中，系统的大致架构如下：
- **数据采集层**：分别开启独立的线程（`thread::spawn`），例如 `sensor_thread`（温湿度）、`weather_thread`（天气）、`tcp_thread`（网络通信与性能指标），大家都各自只管好自己的一亩三分地。
- **全局状态池**：通过 `Arc<RwLock<SystemStatus>>`（在代码中被包装为全局单例 `get_status()`）在内存中维护设备的所有最新状态，作为数据层与 UI 层之间的“解耦桥梁”。
- **UI 渲染核心**：在 `main` 主线程中循环运行，定时读取 `SystemStatus` 的最新快照，利用 `embedded-graphics` 图形库框架绘制到内存缓冲（`FrameBuffer`）中，最后一次性通过 SPI 一票发到 LCD 屏幕上。这就实现了全终端丝滑且无残影的 UI 帧刷新。

## 4. 功能逐一拆解与代码串联

### 4.1 时间、日期与天气：拥抱轻量化网络同步

**应用场景**：
开机连上 WiFi 后，让这块屏幕拥有“全天候感知时序和气象”的能力。

**核心实现**：
首先，在主程序里我们初始化了 ESP 自带的 SNTP 服务建立底层长连接：
```rust
// SNTP 时间同步开启
let _sntp = EspSntp::new_default()?;
```
一旦同步完成，UI 每刷新一帧时，都会通过 `SystemTime::now()` 拿到 Unix 时间戳，并加上 8 小时的时区偏移推算出当前的中国区日期，更新给 `SystemStatus`。

针对外界的天气获取，我们跑了一个独立的 `weather_thread`：
```rust
// fetch_weather 函数内部通过建立普通 TCP Stream 连接 wttr.in 
let request = format!("GET /{}?format=%l@%C@%t@%w ...", city);
stream.write_all(request.as_bytes())?;
```
这里利用了黑客们都知道的神器 API——`wttr.in`。我们发送带有 `format` 参数的 HTTP 请求，获取已经被格式化好的字符串（如 `Shanghai@Cloudy@22@15`）。这样**彻底避开了引入庞大的 JSON 解析库**，在内存寸土寸金的单片机上异常高效。按 `@` 切分并提取温度、风速后就能直接塞爆全局状态池了。

最后由 UI 层面的 `draw_time` 函数，配合等宽字体 `MonoTextStyle` 将这段数据文本美观地展示到界面的醒目位置。

### 4.2 主机 CPU 和内存读取：定制极简 TCP 协议

**应用场景**：
通过无线网抓取电脑里的 CPU 负荷。这就需要一台服务器端，和一台硬件上的消费端。

**核心实现**：
目光转向底层的 `tcp_thread`。我们在电脑端（Host端）跑一个简易的监控服务端推送主机数据，而在盒子内的客户端这边接收数据。
为了追求极致传输速度与极低延迟，我们在底层 Socket 通信上定义了形如 `[MAGIC_HEADER, MSG_TYPE, LEN, PAYLOAD...]` 这样的**极简私有二进制帧协议**。它比 HTTP 和 Websocket 的开销要小多个量级：
```rust
// 在 tcp_thread 的无限循环中解析服务器包
match msg_type {
    crate::protocol::MSG_METRICS => {
        let cpu = payload[0];
        let mem = payload[1];
        if let Ok(mut status) = crate::get_status().write() {
            status.cpu_usage = cpu; // 数据入池
            status.mem_usage = mem;
        }
    }
    // ...
}
```
有了上面这一出，CPU 百分比数据就成功被“偷渡”到了设备里。

为了 UI 上视觉张力，我们还进一步施展了“像素放缩术”（`ScaledDisplay`）。因为原厂附带字体画出来并不够震撼，我们以 `FONT_10X20` 字体的原始字形为基板，向 LCD 原生像素进行了几何多重倍率放大缓冲，毫无压力地画出了极具赛博破坏风的粗直数值图形。

### 4.3 I2C 硬件通信：AHT30 温湿度环境采集

**应用场景**：
设备内的 AHT30 温湿度传感器硬件接口通信与物理温湿度换算。

**核心实现**：
因为 ESP32 只有两根 I2C 总线，往往多种传感器（比如 IMU 和本模块）需要串接在同一根管脚上复用。基于 Rust 的安全性原则，我们把这个 `I2cDriver` 装进了兼具并发安全和互斥性的 `Arc<Mutex>` 并发胶囊里。
```rust
let i2c1_driver = i2c::I2cDriver::new(...)?;
let i2c1_shared = std::sync::Arc::new(std::sync::Mutex::new(i2c1_driver));

// 将胶囊传递给采集线程克隆体
thread::spawn(move || sensor_thread(i2c1_sensor));
```

顺着进入 `sensor_thread`，里面是一套纯粹的硬件地址八股文：对 0x38 设备地址写初始化 `[0xBE, 0x08, 0x00]`；接着写入触发启动测量 `[0xAC, 0x33...]`；延时几十毫秒后再读回那 7 个关键量测结果。随后靠规格书里的数据格式协议算出精度浮点的湿度及温度：
```rust
let temp = (temp_raw as f32) * 200.0 / 1048576.0 - 50.0;
```
由于这些底层的 I2C 获取和延时被单独的 `std::thread::spawn` 藏到了后台，中间长达百毫秒的 `sleep` 挂起期间，我们的 UI 渲染引擎可以依然达到接近 60fps 得疯狂刷新率而不受丝毫阻塞。

## 5. 开发过程中的避坑指南

在这套 “UI高速刷新 + 并发网口传感 IO” 结合得项目中，如果不经打磨也会四处碰壁。我总结了三大最容易翻车的点：

#### 🔴 坑 #1：刷屏闪烁与性能瓶颈 (Display Flicker)
起初为了省事遇到新数据就直接往屏幕 SPI 接口乱写，如果多个文字和图标叠加，整个画面会出现从上至下重绘的扫描撕裂感。
**解法**：老老实实在内存中开辟一块局部的 `FrameBuffer` (如 PSRAM 显存概念)。把所有的渲染全部放在内存储位级解决，最终利用 `fill_contiguous` 函数一并倾倒发送，使得硬件的 LCD 重刷是一帧整整齐齐过来的。彻底根治屏闪！

#### 🔴 坑 #2：多线程下的硬件总线争权 (I2C Ownership Deadlocks)
在 Rust 中并发访问未加设封装的同一个外部管脚资源，编译初期就会遭到无情阻止。（多亏了 Rust！）
**坑点总结**：强包裹 `Arc<Mutex<>>` 之后，在拿到硬件使用锁 `lock().unwrap()` 通信完成的瞬间，**必须立刻释放锁**（可以利用 Rust 大括号 `{}` 作用域丢弃机制），绝对不可跨长时间 `thread::sleep` 仍不交出锁匙，否则挂在同一个线路上的高优先级芯片可能会因无法通信而引发内核看门狗饿死复位死机！

#### 🔴 坑 #3：弱网环境与处理引发的“嵌入式恐慌”(Panic)
使用 HTTP 抓外网接口是个危险操作。要是断网返回空报文，或者返回非 ASCII 英文字母导致长度暴涨，由于缺少 C++ 那样的大内存缓存区，利用 `.unwrap()` 或动态分配 `String::from_utf8` 会非常容易在越界时使设备 Crash，满盘皆崩。
**经验之道**：在只有寥寥几 M 内存的设备上，全面回落到基于定长数组 `[0u8; 16]` 的内存替换法。并搭配大量安全的 `cmp::min(16, length)` 控制，格式化变量到屏幕上时也优先改用 `&mut [u8]` 操作原位更新（避开 `format!()` 会分配到堆上的操作）。这样极大限度地扼杀碎片化，它才能 24 小时连续运行永远保持冷静。
